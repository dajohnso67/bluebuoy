# Authorize.Net CIM Continuity from Go

**Verdict: Yes, with caveats.** A new Go application authenticated with the merchant account's API Login ID + Transaction Key can consume the existing CIM vault as-is. Customer profiles and payment profiles are scoped to the merchant (gateway) account, not to the integration that created them: the live production API schema describes `getCustomerProfileIdsRequest` as retrieving "the customer profile ids for **your account**," authentication carries no application/integration identity beyond the account-level credentials, and Authorize.Net explicitly states the same API credentials "can be used on multiple web sites and shopping cart integrations for one account." The existing `customerProfileId` / `customerPaymentProfileId` values therefore remain valid across the FileMaker-to-Go cutover with no re-collection of cards. Caveats: there is no official Go SDK (call the JSON/XML API over HTTPS directly, minding JSON element-ordering and a BOM quirk); card numbers are only ever returned masked (last 4), so the vault cannot be exported — continuity requires staying on Authorize.Net; and an explicit "same vault across legacy CIM SOAP/XML and the current API" statement does not appear in current docs (strongly implied, flagged below as unverified).

- **Date researched:** 2026-09-07
- **Issue:** dajohnso67/bluebuoy#8 ("Authorize.Net CIM continuity from Go")
- **Method:** primary sources only — developer.authorize.net (API reference, feature guides, upgrade guide, change log, testing guide), support.authorize.net KB articles, the live production API schema served at `https://api.authorize.net/xml/v1/schema/AnetApiSchema.xsd`, and github.com/AuthorizeNet. Each claim cites the source actually loaded.

## 1. Profile ID portability (merchant-account scoping)

**Profiles are scoped to the merchant account.** Evidence, all from primary sources:

- The production API schema's own comment on `getCustomerProfileIdsRequest` reads: *"This method is used retrieve the customer profile ids for your account in case they get lost. The merchant must be signed up for the CIM service to use it."* The request body is nothing but `merchantAuthentication` (it extends `ANetApiRequest` with no additional fields), and `getCustomerProfileIdsResponse` returns a flat `ids` array — i.e., the complete list of customer profile IDs for the authenticated merchant account. ([AnetApiSchema.xsd](https://api.authorize.net/xml/v1/schema/AnetApiSchema.xsd), elements `getCustomerProfileIdsRequest` / `getCustomerProfileIdsResponse`)
- **No per-integration ownership exists in the API surface.** `merchantAuthenticationType` identifies only the merchant account (`name` + a credential — see §2). The only integration-identifying field anywhere in a request is the optional `clientId`, whose schema comment says it is merely an *"Identifier of the API client application/SDK/library/binding e.g. PHP-SDK-1.0.9.1, ACTIVE_MERCHANT"* — informational, not an ownership key. ([AnetApiSchema.xsd](https://api.authorize.net/xml/v1/schema/AnetApiSchema.xsd), `ANetApiRequest` / `merchantAuthenticationType`)
- Authorize.Net's credentials KB states: *"The API ID and related Keys can be used on multiple web sites and shopping cart integrations for one account."* ([KB 000001271](https://support.authorize.net/knowledgebase/article/000001271/en-us))
- The Customer Profiles operations — Create/Get/Update/Delete Customer Profile, Get Customer Profile IDs, Create/Get/Update/Delete Customer Payment Profile, Create a Customer Profile from a Transaction — are all listed in the current API reference and take only `merchantAuthentication` plus the profile IDs; nothing in the Customer Profiles feature guide mentions integration- or application-level profile ownership. ([API reference](https://developer.authorize.net/api/reference/); [Customer Profiles feature guide](https://developer.authorize.net/api/reference/features/customer-profiles.html))
- **Charging a stored profile:** `createTransactionRequest`'s `transactionRequestType` carries an optional `profile` element of type `customerProfilePaymentType` (`customerProfileId` + payment profile reference) — the "Charge a Customer Profile" operation in the reference. Any client with valid merchant credentials can submit it against any profile ID in the account. ([AnetApiSchema.xsd](https://api.authorize.net/xml/v1/schema/AnetApiSchema.xsd), `transactionRequestType` / `customerProfilePaymentType`; [API reference](https://developer.authorize.net/api/reference/), "Charge a Customer Profile")

## 2. Auth model

- **Credentials:** `merchantAuthentication` takes `name` (*"Merchant's unique API Login ID"*) and `transactionKey` (*"Merchant's unique Transaction Key"*). ([API reference](https://developer.authorize.net/api/reference/)) The schema shows `transactionKey` is one of a choice that also includes `sessionToken`, `password`, `impersonationAuthentication` (partner), `fingerPrint`, `clientKey`, and `accessToken` (OAuth). ([AnetApiSchema.xsd](https://api.authorize.net/xml/v1/schema/AnetApiSchema.xsd), `merchantAuthenticationType`)
- **Where obtained:** in the Merchant Interface under **Account > Security Settings > API Credentials & Keys**. The KB describes the purpose: the API Login ID and Transaction Key *"connect your website or other integrated business application to the Authorize.net Payment Gateway for transaction processing."* ([KB 000001271](https://support.authorize.net/knowledgebase/article/000001271/en-us); the "New Experience 2.0" variant is [KA-07619](https://support.authorize.net/knowledgebase/article/KA-07619/en-us))
- **Key rotation timing:** when generating a new Transaction Key you may *"check the box labeled Disable Old Transaction/Signature Key Immediately"*; if unchecked, *"the old Transaction or Signature Key will automatically expire in 24 hours."* So at most two keys overlap, and only within that 24-hour window — there is no support for multiple long-lived concurrent transaction keys. Practical migration consequence: the Go app can either reuse the existing key or generate a new one, but generating a new one kills the FileMaker integration's key within 24 hours (or immediately). ([KB 000001271](https://support.authorize.net/knowledgebase/article/000001271/en-us))
- **Signature Key:** used for hash/response verification (message hash sent with notifications for SIM/Direct Post-era verification; SHA-512 response hashing) — **not** for API authentication. ([KB 000001271](https://support.authorize.net/knowledgebase/article/000001271/en-us))
- **OAuth 2.0:** documented (access token in `merchantAuthentication`/`Bearer` header, 1-hour access tokens, 1-year refresh tokens) but gated — application registration goes through the Partner Interface and sandbox OAuth credentials require emailing developer_feedback@authorize.net. Not the practical path for a single-merchant app; API Login ID + Transaction Key is the standard. ([OAuth feature guide](https://developer.authorize.net/api/reference/features/oauth.html))

## 3. Go API/SDK surface

- **No official Go SDK.** The AuthorizeNet GitHub org's SDKs are: `sdk-dotnet`, `sdk-java`, `sdk-php`, `sdk-python`, `sdk-ruby`, `sdk-node`, plus mobile/in-person SDKs (`inperson-sdk-ios/android/windows`, `accept-sdk-ios/android`). No `sdk-go` exists. ([github.com/orgs/AuthorizeNet/repositories](https://github.com/orgs/AuthorizeNet/repositories))
- **The API is plain HTTPS POST**, so Go's `net/http` + `encoding/json` suffices. Endpoints, from the API reference: production `https://api.authorize.net/xml/v1/request.api`, sandbox `https://apitest.authorize.net/xml/v1/request.api`; content type `text/xml` or `application/json`. ([API reference](https://developer.authorize.net/api/reference/)) JSON support was added (as beta) on 2014-11-17 per the change log. ([API change log](https://developer.authorize.net/api/changes.html))
- **JSON element-ordering quirk is officially documented:** *"While JSON does not typically require a set order to elements in an object, XML requires strict ordering. Developers … should force the ordering of elements to match this API Reference."* (The JSON is translated to XML internally, so out-of-order fields cause E00003-style parse errors.) In Go, define struct fields in schema order — Go's `encoding/json` emits fields in declaration order, which makes this easy; do not marshal from maps. ([API reference](https://developer.authorize.net/api/reference/))
- **BOM quirk:** JSON responses are prefixed with a UTF-8 byte-order mark, which breaks strict JSON decoders; strip `\xEF\xBB\xBF` before unmarshalling. Acknowledged on the Authorize.Net-operated developer community forum, but **not** in the formal API reference — see "What remains unverified." ([community thread "JSON issues"](https://community.developer.authorize.net/t5/Integration-and-Testing/JSON-issues/td-p/48851/page/2))
- Community Go libraries exist (e.g., ports on GitHub) but are **UNOFFICIAL** and not endorsed by Authorize.Net; given the small surface Blue Buoy needs (profiles + transactions), direct `net/http` calls are the safer choice.

## 4. Sandbox verification path

- **Sandbox is a completely separate environment.** Testing guide: *"The sandbox environment is completely separate from the live production environment and requires separate credentials."* Using production credentials against sandbox (or vice versa) yields error 13. Production CIM profiles are therefore **not visible** in sandbox — sandbox proves the *mechanics*, not the *data*. ([Testing guide](https://developer.authorize.net/hello_world/testing_guide/)) Sandbox signup is at the Developer Center; *"No actual card processing is performed. The sandbox only simulates connections to the card networks."* ([Sandbox signup](https://developer.authorize.net/hello_world/sandbox.html))
- **Test Mode caution:** transactions submitted in Test Mode *"are not stored and will return a transaction ID of zero"* — the testing guide says to keep the sandbox in Live Mode; the same applies to production Test Mode, which is useless for verifying profile charging end-to-end. ([Testing guide](https://developer.authorize.net/hello_world/testing_guide/))
- **Validating against production data without a real charge — `validationMode`:** the schema defines `validationModeEnum` = `none` | `testMode` | `liveMode`, accepted on `createCustomerProfileRequest`, `createCustomerPaymentProfileRequest`, `updateCustomerPaymentProfileRequest`, and required on `validateCustomerPaymentProfileRequest`. ([AnetApiSchema.xsd](https://api.authorize.net/xml/v1/schema/AnetApiSchema.xsd)) Per the Customer Profiles feature guide: **liveMode** *"generates a transaction to the processor in the amount of 0.01 or 0.00. If successful, the transaction is immediately voided"* (Visa $0.00; other card types $0.01); **testMode** does field/Luhn validation only and *"is not authorized at the processor, and does not appear on the customer's card statement."* ([Customer Profiles feature guide](https://developer.authorize.net/api/reference/features/customer-profiles.html)) `validateCustomerPaymentProfileRequest` is the purpose-built way to exercise an **existing** stored card without charging it.
- Read-only calls (`getCustomerProfileIdsRequest`, `getCustomerProfileRequest`, `getCustomerPaymentProfileRequest`) create no transactions at all and are safe first probes in production.

## 5. Profiles created by another integration; legacy CIM API

- **No documented constraint** ties a profile to the integration that created it. Neither the API reference, the Customer Profiles feature guide, nor the CIM KB mentions any restriction on charging/reading/updating profiles created by a different client of the same merchant account (see §1 evidence). CIM is described as a merchant-account service; even on service discontinuation *"the payment gateway will store any customer payment profiles for up to a year before purging them from our system."* ([KB KA-04443, "What is Customer Information Manager (CIM)…"](https://support.authorize.net/knowledgebase/Knowledgearticle/?code=KA-04443))
- **Legacy API status:** *"We have deprecated our SOAP API that offered support primarily for Customer Information Manager."* Replacement: *"The Authorize.net API includes all of the SOAP API functionality plus additional features such as Authorize.net Accept, creating one-time transactions and enhanced Customer Profile methods."* ([Upgrade guide](https://developer.authorize.net/api/upgrade_guide.html)) Change-log markers: SOAP API deprecated 2016-11-07; hosted CIM forms EOL'd (HTTP 410 after 2018-09-20) with users *"migrated to Accept Customer."* ([API change log](https://developer.authorize.net/api/changes.html); [Upgrade guide](https://developer.authorize.net/api/upgrade_guide/)) The legacy CIM XML method names (`createCustomerProfileRequest`, etc.) are the *same* element names in today's schema — the current API is the continuation of the CIM XML API rather than a parallel system. ([AnetApiSchema.xsd](https://api.authorize.net/xml/v1/schema/AnetApiSchema.xsd))
- **Masked data only — the vault cannot be exported.** The schema makes this structural: `getCustomerProfileResponse` / `getCustomerPaymentProfileResponse` return `customerPaymentProfileMaskedType`, whose `payment` is `paymentMaskedType` (`creditCardMaskedType` / `bankAccountMaskedType`); `creditCardMaskedType.cardNumber` is a string of **exactly length 8** (i.e., `XXXX1111` — last four only). Full PAN is never retrievable, so card data cannot be migrated off Authorize.Net via the API; continuity requires staying on the same merchant account's vault (the rationale behind issue rule 6). ([AnetApiSchema.xsd](https://api.authorize.net/xml/v1/schema/AnetApiSchema.xsd))
- **Expiration dates:** masked by default; `getCustomerProfileRequest` and `getCustomerPaymentProfileRequest` accept optional `unmaskExpirationDate` (boolean) and `includeIssuerInfo` fields. The masked expiration is a 4-char `XXXX`, unmasked is up to 7 chars (`YYYY-MM`) per the schema string lengths. Change log: unmasked expiration retrieval added for GetCustomerPaymentProfile 2015-11-03 and for GetCustomerProfile 2016-08-10. So the Go app **can** read real expiry dates for renewal/dunning logic. ([AnetApiSchema.xsd](https://api.authorize.net/xml/v1/schema/AnetApiSchema.xsd); [API change log](https://developer.authorize.net/api/changes.html))

### Limits and endpoint notes

- **Per-profile limits:** *"Each customer profile can include up to 10 payment profiles and up to 100 shipping profiles."* No maximum number of customer profiles per merchant account is documented. ([KB KA-04443](https://support.authorize.net/knowledgebase/Knowledgearticle/?code=KA-04443))
- **API rate limits:** none published in the API reference, feature guides, or KB articles reviewed.
- **Akamai/firewall guidance:** *"For API endpoints behind Akamai SureRoute, we are not able to provide IP addresses, due to the nature of Akamai address allocation"* — merchants should *"allow Internet traffic from any IP address"* (or use domain-level whitelisting on modern firewalls). The `api2.authorize.net` / `secure2.authorize.net` names were the Akamai transition-era endpoints; new work should use `api.authorize.net`, which the API reference lists as the production endpoint. ([Domains and IP addresses](https://developer.authorize.net/api/domains_addresses.html); [API reference](https://developer.authorize.net/api/reference/))

## What remains unverified

1. **An explicit statement that profiles created via the legacy CIM SOAP/XML API remain usable via the current JSON API ("same vault").** The upgrade guide says the current API "includes all of the SOAP API functionality" and the schema retains the same CIM request names, and the CIM KB treats the vault as an account-level store — but no page says in one sentence "existing profiles carry over across API versions." UNVERIFIED as an explicit doc statement; strongly implied. The production read-only probe below settles it empirically in minutes.
2. **The BOM in JSON responses** is acknowledged only on the Authorize.Net-run community forum, not in the formal API reference. Treat as an observed behavior to defend against (strip a leading `\xEF\xBB\xBF` unconditionally), not a documented contract.
3. **Which API the FileMaker plugin actually used** (legacy CIM XML/SOAP vs. current endpoint) — unknowable from Authorize.Net docs; irrelevant to portability if scoping holds, but worth confirming from the plugin's config during the production probe.
4. **`validationMode: none` behavior** is present in the live schema's enum, but the current Customer Profiles feature guide documents only testMode/liveMode behavior; "none" (skip validation entirely) is carried over from legacy CIM docs. Minor.
5. **API Login ID length**: the API reference says 20-char max while the live schema allows 25 — trivially inconsistent between Authorize.Net's own sources; irrelevant to the migration.
6. **Rate limits / max customer profiles per account**: not documented anywhere reviewed; absence of a documented limit is not proof none exists.

## Recommended cutover verification sequence

Sandbox first (proves the Go client), then production read-only (proves the vault), then one controlled validation (proves charging):

1. **Sandbox** ([signup](https://developer.authorize.net/hello_world/sandbox.html)): build the Go client against `https://apitest.authorize.net/xml/v1/request.api`; create a profile + payment profile with a [test card](https://developer.authorize.net/hello_world/testing_guide/), then exercise `getCustomerProfileIds`, `getCustomerProfile` (with `unmaskExpirationDate: true`), `validateCustomerPaymentProfile` (liveMode), and `createTransaction` with a `profile` payment. This flushes out JSON ordering/BOM handling before production credentials are involved.
2. **Production, read-only:** with the merchant's API Login ID + Transaction Key against `https://api.authorize.net/xml/v1/request.api`, call `getCustomerProfileIdsRequest` — a successful `ids` array containing the FileMaker-era profile IDs is direct proof of merchant-level scoping. Then `getCustomerProfileRequest` on one known profile and confirm the masked card + real expiry match FileMaker's records. Zero transactions are created.
3. **Production, one validation:** `validateCustomerPaymentProfileRequest` with `validationMode: liveMode` on one consenting customer's stored card — $0.00/$0.01 auth, immediately voided per the [feature guide](https://developer.authorize.net/api/reference/features/customer-profiles.html). (Alternative: a small auth-only `createTransactionRequest` against the profile followed by `voidTransaction`.)
4. **Key handling at cutover:** reuse the existing Transaction Key if it is recoverable from FileMaker's config; if a new key must be generated, remember the old key dies within 24 hours (or immediately if the disable box is checked) — schedule FileMaker's shutdown accordingly. ([KB 000001271](https://support.authorize.net/knowledgebase/article/000001271/en-us))
